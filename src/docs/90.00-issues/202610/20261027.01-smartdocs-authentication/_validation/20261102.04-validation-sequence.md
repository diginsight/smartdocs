# Validation sequence — end-to-end access validation

This run executes `WS-F-end-to-end-validation` of [the implementation plan](../01-roles-permissions-support.plan.md). It supersedes the [blocked preflight of 2026-10-28](20261028.04-validation-sequence.md), which stopped before its first scenario.

The run shows six things:

- A metadata push reaches only the readers whose role set sees the changed space.
- A removed role stops opening its spaces at the end of the session, or at the next sign-in.
- Protected responses are cached privately and refused before any entity tag is compared.
- Every anonymous response is byte-identical to the baseline commit's.
- An unreadable, invalid, or missing access file closes its space.
- A hidden root-mounted space leaves no trace for readers who can't see it.

It also resolves `DS-4-hub-expiry` on its positive branch. One concealment defect surfaced in `F6-mount-route-divergence` and was fixed during the run. The final build passes every scenario.

## Fixes made during the run

1. **A hidden root-mounted space removed the root's Home link.** `ReaderAccess.FilterLevelAsync` kept each node whose source folder the reader can see. The source folder of the site root's generated **Home** link is the root itself, which the root-mounted space owns. So when an anonymous reader couldn't see `home`, the link was dropped (screenshots 28 and 29). A site with no root-mounted space keeps that link, because the root then belongs to no space and takes the verdict for content outside every space. The link's absence therefore revealed that a hidden space claims the root, which `D3-unauthorized-response` forbids.

   The filter now decides that one link by what `/` shows. The link is the only node with the empty route that isn't a section. `/` shows either the root-mounted space's page or the generated index, so the link stays visible when the reader sees the root-mounted space, or when the reader sees content outside every space. With no root-mounted space, the new rule gives the same verdict as the old one, so rows 1 to 9, whose fixture mounts nothing at the root, aren't affected. Row 7's final capture was taken with the fix in place. After a rebuild with 0 warnings and 0 errors, row 10's seven surfaces were byte-identical between the two sites.

## Notes

**Not covered by this run:**

- A production deployment. The deployed certificate and authorization code flow, the deployed `Site:InvalidateApiKey`, and real reader accounts belong to `PL-7-deployed-registrations`.
- Phone widths. Every screenshot is at 1280×800.
- More than one test account. `DS-3-test-accounts` took its negative branch, so each persona is the same account with different memberships.

**Deviations and observations:**

- **`F4-regression` used a clone, not a worktree.** The plan's `git worktree add` produced a build that crashed at startup. Diginsight's configuration extension looks for a `.git` *folder* to find the repository root, and a worktree has a `.git` *file*, so the lookup returned no path. The baseline was checked out with `git clone --shared --no-checkout` followed by a checkout of the baseline commit, and deleted afterwards with `Remove-Item`. `SIG-4` on [the signals page](../02-signals.md) records the extension's defect.
- **New memberships reach ID tokens with a delay.** In row 3, the first sign-in after adding the account to *Product B readers* still carried the old roles. The new role appeared about 75 seconds later. A removal showed up at a sign-in 38 seconds after it.
- **The open session kept its role until expiry, as `D9-explicit-session-lifetime` designs.** Row 2's positive control shows that a removed role keeps working in an open session until the session lifetime ends. The hub then closes, and the client reconnects anonymously. The reconnection updated the sidebar and footer at once, while the top bar and the space cards kept the spaces the reader had already been shown until the reload.
- **The footer's section line lags a push.** In row 1, the footer on Product B's page read *Product B: 1 articles* while the total read 8, because only the total is refreshed by a push. Hovering the section showed the right count. This is a display delay, not an access leak, and `SIG-3` records it.
- **One sign-in failed with "Correlation failed" at 17:28:33Z.** The test harness opened the callback without its correlation cookie. Nothing in the product caused it, but the developer error page it produced shows that a failed sign-in has no handler, which `PL-22-sign-in-remote-failure` tracks.
- **`/_nav/version` answers anonymous readers.** Its number rises on every invalidation, including one for a hidden space. It reveals only that something changed, has done so since the baseline, and is tracked by `PL-21-nav-version-side-channel`.
- **`POST /_nav/invalidate` was open locally.** The overlay sets no `Site:InvalidateApiKey`, and the endpoint enforces a key only when one is configured. Deployed hosts must set it, and `PL-7-deployed-registrations` verifies it.
- **`SIG-1` recurs, and `SIG-5` is new.** The `ComponentStatePersistenceManager` `Error` still appears on every page. Once, 38 ms after one of them, `NavigationBootstrapMiddleware` failed to set `Content-Length` on a response that had already started. Both predate this work item.
- **Every change was undone.** Memberships returned to no group, the overlay and `product-a`'s access file returned to their original bytes, every probe was deleted, the baseline clone was removed, and the host was stopped.
