## 🎯 Goal

Rename the raw passthrough route from `/_content-raw` to `/_content`, in the host endpoint, the shared renderer, the browser client and the documentation that publishes it — as one lockstep change, so the three tiers never disagree.

## 🧭 Why this plan exists

`/_content-raw` is harder to recall and to type than it needs to be, and the `-raw` suffix describes an implementation detail rather than what a caller gets. The route is not a stable public contract: it is consumed by this application's own client and emitted by this application's own renderer.

The change is trivial in isolation and dangerous if partial. The literal is **duplicated in three projects with no shared constant**, and two of the three tiers emit it in a *different shape* — root-absolute in the renderer, base-relative in the client. If the endpoint moves and the renderer does not, every image on every page 404s, and nothing fails at build time to say so.

## 🔍 Blast radius

Every occurrence, read from source on 2026-09-04. The token `_content-raw` is unique in the repository, so each is an unambiguous replace target.

## 🧩 Decisions taken

Both were put to the user as questions; the user was unavailable and delegated the call. Both are recorded here so the choice is reviewable rather than implicit.

### D1-use-requested-content-prefix — the new literal is `/_content`, as requested

`/_content/` is ASP.NET Core's **reserved base path for Razor Class Library static web assets** (`/_content/{PackageId}/…`), so the application will no longer fully own that prefix.

Chosen anyway, because the request was explicit and the risk is negligible in this repository:

- Neither `Diginsight.SmartDocs.Web.Shared` nor `Diginsight.SmartDocs.Web.Client` ships a `wwwroot`, and the build emits **no** `_content/` base path today — verified against `staticwebassets.build.json`.
- Even if an RCL later shipped assets, a literal route segment outranks a catch-all parameter in ASP.NET Core routing, so the static asset would win its own exact path and `/_content/{**key}` would continue to serve everything else. The failure mode would be a *shadowed content key* literally named `_content/{PackageId}/…`, and keys beginning `_` are already excluded from navigation.

**Guard:** if a referenced RCL ever gains static web assets, re-open this choice rather than absorbing the ambiguity.

### D2-hard-rename-without-alias — `/_content-raw` is not kept

No redirect, no alias. Rationale:

- HTML is rendered **per request**, and `CachedContentSource` caches *source bytes*, not rendered output — so no cached artefact pins the old URL.
- The whole exposure is HTML already sitting in a browser tab across a deploy: one refresh fixes it.
- The motivation for the rename is simplicity. A permanent second route serving the same bytes works against that.

Reversible: re-adding a compatibility route later is a one-line `MapGet`.
