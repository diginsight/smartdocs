# Validation sequence — raw content endpoint rename

## 🎯 What this proves

That renaming the raw passthrough route from `/_content-raw` to `/_content` left the three tiers in agreement: the host serves the new route, the shared renderer emits it, and the WASM client requests it — while the old route no longer resolves.

## 🧾 Run context

| Item | Value |
|---|---|
| Date | 2026-09-04 |
| Host | `dotnet run --project src\Diginsight.SmartDocs.Web --urls http://localhost:5280`, visible terminal, full rebuild |
| Configuration | `Development` — one space at `RouteBase: "/"`, `RootPath: ..\docs` |
| Build | `dotnet build src\Diginsight.SmartDocs.slnx` — succeeded, 0 errors, 0 warnings |
| Browser | Chromium, 1400×900 viewport |

## 🔬 Sequence

| Step | Observation | Evidence |
|---|---|---|
| **Step 1** — a page embedding a relative image is opened. The renderer rewrote the image URL to the new prefix, and the browser decoded the image at its natural size of 1440×1000, which a broken image could not report. The rendered HTML contained **2** occurrences of `/_content/` and **0** of `/_content-raw`. | `src` resolved to `/_content/90.00-issues/202608/20260817.01-deployfail/_validation/images/01-site-index.png` | ![Documentation page rendered in the browser with its embedded screenshot image loaded through the renamed /_content route](images/01-image-served-via-content-route.png) |
| **Step 2** — client-side navigation. From Getting Started, the Security link was clicked; the page did not reload (a flag set on `window` before the click survived it) and the article rendered with heading *Security posture*. The client requested `/_content/02.00-getting-started.md`, `/_content/02.00-getting-started/index.md` and `/_content/09.00-security/01-security-posture.md` — the candidate ladder walking the renamed endpoint. | `HttpContentSource` reaches `/_content` | ![Security posture article rendered after an in-app navigation that did not reload the page](images/02-client-side-navigation.png) |
| **Step 3** — the old route. `/_content-raw/index.md` no longer matches an endpoint and falls through to the catch-all page component, which reports *No Markdown source resolved for `_content-raw/index.md`*. | The old surface is gone, not shadowed | ![Application shell showing a Not found heading and the message No Markdown source resolved for _content-raw/index.md](images/03-old-route-no-longer-served.png) |

## 📋 Endpoint probes

Run against the same instance. Byte counts distinguish real content from the ~16 KB application shell the catch-all returns.

| Request | Result |
|---|---|
| `GET /_content/index.md` | 200, 5 142 bytes of Markdown |
| `GET /_content/06.00-reference/02-http-endpoints.md` | 200, 5 884 bytes of Markdown |
| `GET /_content/…/images/01-site-index.png` | 200, `image/png`, 19 432 bytes |
| `GET /_content-raw/index.md` | 200 but 16 311 bytes — the application shell, identical for any key, i.e. no endpoint match |
| `GET /_content-raw/06.00-reference/02-http-endpoints.md` | 200 but 16 339 bytes — same shell |

## ⚠️ Observed but not caused by this change

`GET /_content/LICENSE` returns 404, and the **About → License** menu item therefore does not resolve. `LICENSE` sits at the repository root while the configured content root is `src\docs`, so the file was never inside the served tree — `/_content-raw/LICENSE` returned 404 before the rename for the same reason. This is the pre-existing `G2-about-menu-hardcoded-hrefs` defect, parked in the plan rather than fixed here.

## ✅ Outcome

Pass. All three browser cases behaved as intended and no regression was observed.
