# Configure CI/CD credentials, secrets and grants for diginsight/smartdocs

The four deployment workflows in this repository are written and committed, and none of them can run yet. They depend on things that live outside the code — a federated identity credential in Entra ID, role assignments in Azure, a read token for the private configuration repository, and nine repository secrets. This guide creates all of them, in the order that lets each step verify the one before it.

You will need: **Owner** or **User Access Administrator** on the target subscription, permission to modify the existing Entra application, and **admin** on the `diginsight/smartdocs` repository.

**Status at 2026-08-17** — Steps 1, 2 and 5 are complete. The Azure side is fully configured; nothing in the subscription blocks a deployment any longer. What remains is entirely GitHub-side: the token in Step 3 and the nine secrets in Step 4, and until those exist no workflow can run at all.

## 🎯 What this configures

Four workflows, three identities, two directions of trust.

| Workflow | Purpose | Needs |
|---|---|---|
| `00.BuildSmartDocsWeb.yml` | Reusable build and deploy — called, never triggered | All of the below, passed in by its caller |
| `01.DeployLearnHub.yml` | Deploys the learning-hub site | OIDC, internal read token, host name |
| `02.DeployDocsSite.yml` | Deploys the documentation site | OIDC, internal read token, host name |
| `03.PublishDocsContent.yml` | Mirrors `src/docs` into blob storage | OIDC, storage account and container names |

The identities involved are distinct and easy to conflate:

| Identity | Who it is | What it may do |
|---|---|---|
| **Workflow identity** | The Entra application GitHub Actions federates into | Deploy and configure the App Services; **write** content blobs |
| **Learning-hub site identity** | System-assigned managed identity on the learning-hub App Service | **Read** its own content container |
| **Documentation site identity** | System-assigned managed identity on the documentation App Service | **Read** its own content container |

The sites never write and the workflow never renders. Keeping those separate is why a compromised site cannot alter the content it serves.

> **No real names appear in this guide.** This repository is public. Storage account, container, resource group and App Service names live in `diginsight/smartdocs.internal` and in the secrets you are about to create. Placeholders below are written as `<PLACEHOLDER>` — substitute from the internal repository, never from memory.

## 🔒 Why there are only five secrets

An earlier revision of the convergence plan made **every** workflow value a secret — host names, storage account, container — reasoning that this repository is public, that GitHub masks secrets but not variables, and that a host name echoed by `az webapp show` in a world-readable log is an attacker's starting point.

The masking argument was sound; the conclusion was not. Those values were **already** in `diginsight/smartdocs.internal`, where the serving host reads them from: `Site:Spaces[]` carries `Blob.AccountUri` and `Blob.ContainerName` per space, and the App Service name now sits in a `Deployment` block in the same file. Storing them again as secrets created a second copy that nothing kept in agreement — change a container in the overlay and the publishing workflow keeps writing to the old one, so the site goes empty while neither value is individually wrong.

The workflows therefore read all of them from the overlay and call `::add-mask::` on each before it can reach a log line. That single line preserves everything the secrets were providing, and the four configuration secrets are gone.

**Do not create `SMARTDOCS_LEARNHUB_WEBAPP_NAME`, `SMARTDOCS_DOCS_WEBAPP_NAME`, `SMARTDOCS_STORAGE_ACCOUNT` or `SMARTDOCS_DOCS_CONTAINER`.** They appear in earlier revisions of the plan and in nothing the workflows read.

| Plan said | Workflows actually read |
|---|---|
| `INTERNAL_REPOSITORY_TOKEN` (secret) | `SMARTDOCS_INTERNAL_READ_TOKEN` |
| `SMARTDOCS_WEBAPP_NAME` / `SMARTDOCS_LEARNHUB_WEBAPP_NAME` | *not used* — `Deployment:WebAppName` in `appsettings.Testmc.json` |
| `DOCS_WEBAPP_NAME` / `SMARTDOCS_DOCS_WEBAPP_NAME` | *not used* — `Deployment:WebAppName` in `appsettings.TestmcDocs.json` |
| `SMARTDOCS_RESOURCE_GROUP` (variable) | *not used* — resolved at runtime from the App Service name |
| `SMARTDOCS_STORAGE_ACCOUNT` | *not used* — `Site:Spaces[].Blob.AccountUri` |
| `SMARTDOCS_DOCS_CONTAINER` | *not used* — `Site:Spaces[].Blob.ContainerName` |

One consequence to note before Step 4: `03.PublishDocsContent.yml` now checks out `smartdocs.internal` too, so the internal read token is required for content publishing and not only for deployment.

## 🔑 Step 1 — Add the federated credential

> ✅ **Done 2026-08-17.** The credential `smartdocs-main` was added to the existing application, alongside the pre-existing credential for the predecessor repository — which was left in place, because that repository still deploys from it.

A federated credential is scoped to **one repository and one subject**. The credential that authenticates `diginsight/tools` will not authenticate a workflow running in `diginsight/smartdocs`, and the failure message names neither.

Extend the **existing** application rather than creating a new one — it already holds the role assignments on the App Services and the storage account, and a new application would need every one of them re-granted.

Find out what is already there before adding anything. The application that deployed the predecessor site is the one to extend, and its existing credential names the repository it was created for:

```powershell
az login
$appId = "<AZURE_CLIENT_ID>"

az ad app show --id $appId --query "{displayName:displayName, appId:appId}" -o json
az ad app federated-credential list --id $appId --query "[].{name:name, subject:subject}" -o table
```

Then add the credential for this repository — a credential is additive, and the existing one must be left in place while the predecessor repository still deploys:

```powershell
$fic = @'
{
  "name": "smartdocs-main",
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:diginsight/smartdocs:ref:refs/heads/main",
  "audiences": [ "api://AzureADTokenExchange" ]
}
'@

# BOM-free on purpose: the CLI cannot parse an @file argument that starts with a UTF-8 BOM,
# and Windows PowerShell's Set-Content -Encoding utf8 writes one.
[System.IO.File]::WriteAllText("$PWD\fic.json", $fic, (New-Object System.Text.UTF8Encoding $false))

az ad app federated-credential create --id $appId --parameters "@$PWD\fic.json"
Remove-Item "$PWD\fic.json"
```

Confirm it landed, and that the subject is character-for-character what you expect:

```powershell
az ad app federated-credential list --id $appId --query "[].{name:name, subject:subject}" -o table
```

**The subject must match how the workflow is triggered.** All four workflows run on the `main` branch — push, `workflow_dispatch` and `repository_dispatch` all produce `ref:refs/heads/main`. None of them declares a job-level `environment:`, which would change the subject to `environment:<name>` and silently invalidate this credential. If you later add an environment for approval gates, add a second federated credential for it.

## 🛡️ Step 2 — Grant the workflow identity its Azure roles

> ✅ **Done 2026-08-17 — no commands were run.** The audit below showed the principal already holds both grants, inherited from the predecessor deployment: `Contributor` at the App Services resource group (a superset of `Website Contributor`) and `Storage Blob Data Contributor` at the content storage account. Creating narrower duplicates alongside them would add access-review noise and change nothing.

**Audit before you grant.** If the application was reused from a predecessor deployment it very likely already holds both assignments below, and creating them again adds noise to an access review for no benefit.

```powershell
$spId = az ad sp show --id $appId --query id -o tsv
az role assignment list --assignee $spId --all --query "[].{role:roleDefinitionName, scope:scope}" -o table
```

Role assignments target the **service principal**, not the application — `$spId` above, never `$appId`.

**The App Services and the storage account are usually in different resource groups.** Do not carry one `$rg` variable through both grants below; that is the mistake that produces an assignment at a scope where the resource does not exist, which succeeds and then does nothing.

```powershell
$sub       = "<AZURE_SUBSCRIPTION_ID>"
$rgApps    = "<RESOURCE_GROUP_OF_THE_APP_SERVICES>"
$rgStorage = "<RESOURCE_GROUP_OF_THE_STORAGE_ACCOUNT>"
$account   = "<STORAGE_ACCOUNT>"
```

**Deploy and configure both App Services.** `Website Contributor` at resource-group scope covers everything the build workflow does: `az webapp config set`, `az webapp config appsettings set`, and the publish action. A pre-existing `Contributor` at the same scope already covers it — leave it alone rather than adding a narrower duplicate.

```powershell
az role assignment create --assignee-object-id $spId --assignee-principal-type ServicePrincipal `
  --role "Website Contributor" `
  --scope "/subscriptions/$sub/resourceGroups/$rgApps"
```

Resource-group scope is also what makes the runtime lookup work. The workflow does not take a resource group as input — it discovers one with `az webapp list --query "[?name=='...'].resourceGroup"`, and that query returns only sites the caller can read. Grant at a narrower scope and the lookup returns empty, producing `Could not resolve resource group for the target App Service`.

**Write content blobs.** Only `03.PublishDocsContent.yml` needs this, and it needs the data plane, not the control plane — `Contributor` on the storage account does **not** grant blob data access.

```powershell
az role assignment create --assignee-object-id $spId --assignee-principal-type ServicePrincipal `
  --role "Storage Blob Data Contributor" `
  --scope "/subscriptions/$sub/resourceGroups/$rgStorage/providers/Microsoft.Storage/storageAccounts/$account"
```

Account scope rather than container scope here, because the workflow creates the container if it is absent.

Role assignments take up to five minutes to propagate. A run that fails with an authorization error immediately after this step is worth retrying once before you start debugging it.

## 🎫 Step 3 — Create the read token for smartdocs.internal

> ✅ **Done 2026-08-17.** The fine-grained token was created and configured. Record its expiry date in a calendar now if you have not — see the warning at the end of this step.

**All three** workflows check out `diginsight/smartdocs.internal` to fetch the configuration overlay. `01` and `02` need the storage identity and the deployment target; `03` needs the destination container of the space it publishes. The workflow's own `GITHUB_TOKEN` is scoped to this repository alone and cannot reach the internal one.

Create a **fine-grained personal access token**:

| Field | Value |
|---|---|
| Resource owner | `diginsight` |
| Repository access | **Only select repositories** → `diginsight/smartdocs.internal` |
| Repository permissions | **Contents: Read-only** — nothing else |
| Expiration | The shortest period you will realistically renew |

Fine-grained tokens against an organization may require organization approval before they work. If the checkout fails with a *repository not found* error immediately after creation, check the organization's pending token requests before assuming the token is wrong.

**This token expires, and its expiry is the single most likely cause of a future deployment failure** — it will present as a missing repository rather than as an authentication problem. Put the expiry date in a calendar now.

## 🔐 Step 4 — Create the repository secrets

In `diginsight/smartdocs` → **Settings** → **Secrets and variables** → **Actions** → **Repository secrets**.

| Secret | Value | Used by |
|---|---|---|
| `AZURE_CLIENT_ID` | Application (client) ID from Step 1 | 01, 02, 03 |
| `AZURE_TENANT_ID` | Directory (tenant) ID | 01, 02, 03 |
| `AZURE_SUBSCRIPTION_ID` | Target subscription ID | 01, 02, 03 |
| `SMARTDOCS_INTERNAL_READ_TOKEN` | The token from Step 3 | 01, 02, 03 |
| `SMARTDOCS_INVALIDATE_KEY` | A generated shared secret | 01, 02, 03 |

**Five secrets, and no sixth.** Everything else the workflows need — App Service names, storage account, container names — comes from the `smartdocs.internal` overlay at run time. If you find yourself creating a secret that names an Azure resource, stop and re-read the section above.

Generate the invalidation key rather than inventing one, and generate it from a cryptographic source. `Get-Random` is seeded from a predictable source and is not suitable for minting a shared secret:

```powershell
$bytes = [byte[]]::new(32)
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes)
[Convert]::ToBase64String($bytes)
```

That value must be identical in the secret and in `Site:InvalidateApiKey`. The workflow writes it into the App Service settings for you, so setting the secret is sufficient — do not also set it by hand in the portal, or the two will drift and cache invalidation will start returning `401` with no other symptom.

If the secret is left unset the workflows still succeed: the key is optional, and an unset key leaves `/_nav/invalidate` **unauthenticated**. That is acceptable for a local run and not for a deployed site.

Screenshot the resulting list and compare it against the table above before moving on. A missing secret surfaces as an empty string, and an empty string fails much later and much less clearly than a missing one.

## 🪪 Step 5 — Grant each site identity read access to its containers

> ✅ **Done 2026-08-17.** The documentation identity held **no** role assignments at all and now holds container-scoped `Storage Blob Data Reader`. Its container did not exist, so it was created empty first rather than waiting for `03` — see the note below. The learning-hub identity was left on its inherited account-scoped Reader.

The workflow identity writes content; the sites read it. These are separate grants on separate principals.

**A container-scoped assignment requires the container to exist.** If the documentation container has never been populated, either run `03.PublishDocsContent.yml` first — it creates the container — or create it directly, which is the faster path when the secrets of Step 4 are not yet in place:

```powershell
az storage container create --account-name $account --name "<DOCS_CONTAINER>" --auth-mode login
```

An empty container costs nothing and is idempotent with what `03` would have done, so creating it early does not conflict with the publishing workflow.

```powershell
$accountId = "/subscriptions/$sub/resourceGroups/$rgStorage/providers/Microsoft.Storage/storageAccounts/$account"

# Learning-hub site → its own container
$learnMi = az webapp identity show --name "<LEARNHUB_WEBAPP>" --resource-group $rgApps --query principalId -o tsv
az role assignment create --assignee-object-id $learnMi --assignee-principal-type ServicePrincipal `
  --role "Storage Blob Data Reader" `
  --scope "$accountId/blobServices/default/containers/<LEARN_CONTAINER>"

# Documentation site → its own container
$docsMi = az webapp identity show --name "<DOCS_WEBAPP>" --resource-group $rgApps --query principalId -o tsv
az role assignment create --assignee-object-id $docsMi --assignee-principal-type ServicePrincipal `
  --role "Storage Blob Data Reader" `
  --scope "$accountId/blobServices/default/containers/<DOCS_CONTAINER>"
```

**Reader, and scoped per container.** The renderer only ever reads, and per-container scope means onboarding a new space is an explicit, auditable grant rather than something already in force. Account-scoped access would make every future container readable by both sites the moment it is created.

A predecessor deployment may already have granted the learning-hub identity **account-scoped** Reader. That works, and it is exactly the blanket grant this step exists to avoid — narrowing it is a separate change, and it must be made by adding the container-scoped assignment first and removing the account-scoped one second, or the site loses access in between.

If `az webapp identity show` returns empty, the site has no system-assigned identity yet — enable it with `az webapp identity assign` before granting.

## ✅ Step 6 — Verify, in this order

Each check exercises one more layer than the last, so the first failure tells you where the problem is.

1. **Federated credential** — `az ad app federated-credential list` shows subject `repo:diginsight/smartdocs:ref:refs/heads/main`.
2. **Secrets** — all nine present, names matching Step 4 exactly.
3. **Content publish** — run `03.PublishDocsContent.yml` via **Run workflow**. It is the lowest-risk probe: it exercises OIDC login and blob write, and touches no App Service. A green run proves Steps 1, 2 and 4.
4. **Documentation deployment** — do **not** run `02.DeployDocsSite.yml` yet. Its overlay mounts a space at a non-root prefix, which needs work that is still open in the convergence plan; the workflow's smoke check would fail at `/` even with credentials configured correctly.
5. **Learning-hub deployment** — run `01.DeployLearnHub.yml` via **Run workflow**.

> ⚠️ **Step 5 is the cutover.** `01.DeployLearnHub.yml` replaces whatever is currently serving the learning hub. Capture the baseline article URLs first — the convergence plan requires this as `Step I0` — because after this run there is nothing left to compare against.

Read the run log and confirm the deployment named the App Service you intended. A deployment that landed on the wrong host has already overwritten something else, and the log is the only place that says so.

## 🧯 Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `AADSTS700213` / *No matching federated identity record found* | Subject mismatch — wrong repository, wrong branch, or a job-level `environment:` was added | Compare the workflow's actual ref against the credential subject; add a second credential if an environment is now in play |
| `azure/login@v2` fails with no detail | `permissions: id-token: write` missing, or the credential does not exist | Both are present in the committed workflows; check Step 1 |
| `Could not resolve resource group for the target App Service` | The name secret is wrong, or the principal cannot read that site | Verify the secret value, then confirm `Website Contributor` at resource-group scope |
| `remote: Repository not found` on the internal checkout | Token expired, revoked, or awaiting organization approval | Recreate per Step 3 and check pending organization requests |
| *Overlay missing or contains no `Site:Spaces`* | `internal-config-path` points at a file that is absent or malformed | Confirm the overlay exists in `smartdocs.internal` at the exact path the caller passes |
| `HTTP 500.32` after a successful deploy | Worker bitness does not match the published runtime identifier | The workflow sets this every run; re-run and restart the site |
| `AuthorizationPermissionMismatch` on blob upload | `Storage Blob Data Contributor` missing, or control-plane `Contributor` was granted instead | Re-run the data-plane assignment in Step 2 |
| Site renders an empty navigation tree | The site identity cannot read its container | Step 5, and confirm the container name matches the overlay |

## 🏁 Conclusion

Six steps, and the ordering matters more than any individual command: the federated credential must exist before any workflow authenticates, the roles before any workflow acts, and the content publish before the site deployments, because it is the only probe that proves the credentials work without changing a running site.

The two things most likely to break this setup months from now are both time-based — the fine-grained token's expiry and any drift between `SMARTDOCS_INVALIDATE_KEY` and the App Service setting. Neither fails loudly.

**Next**: with credentials in place, the remaining blockers are in the code rather than the configuration. `02.DeployDocsSite.yml` stays parked until non-root route bases render correctly — tracked as `G1-renderer-root-absolute-urls` in [01-smartdocs-web-convergence.plan.md](../01-smartdocs-web-convergence.plan.md).
